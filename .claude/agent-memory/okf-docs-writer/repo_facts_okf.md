## Repo/worktree layout
This repo uses git worktrees: `main` and `feature/frontend-design` can point at the
same commit while a large amount of new work (e.g. the entire `frontend/` React app)
sits as **untracked, uncommitted files** rather than a committed diff. `git diff
main...HEAD` / `git log main..HEAD` can both come back empty even though a real,
finished change exists on disk. When that happens, treat the invocation prompt's
summary as authoritative (per the okf-docs skill's own instruction that it outranks
diff-reading when supplied) and verify specifics by reading the actual source tree
(`package.json`, route files, key modules) rather than relying on git alone.

## documentation/frontend/ mapping
- `documentation/frontend/overview.md` — top-level Frontend concept. Describes stack,
  routes, design-system provenance, and links out to the two sub-concepts below. Do
  not fold the honesty rules or generated-types workflow back into this file; they
  were deliberately split out as their own concepts.
- `documentation/frontend/honesty-rules.md` — one concept covering all ten "honesty
  rules" the frontend enforces about search-result data (appendix attribution, no raw
  `score`, `total` is a candidate pool not a corpus count, declared vs inferred
  entities, unresolved citations as text not links, etc). Source of truth in code:
  `frontend/src/components/research/honesty-rules.test.tsx` — one test/describe block
  per rule. When code changes there, re-check this concept.
- `documentation/frontend/generated-types.md` — the `npm run gen:types` /
  `openapi-typescript` workflow (`frontend/scripts/gen-types.mjs` →
  `src/api/schema.d.ts`, committed, generated by importing the FastAPI app rather than
  hitting a running server).

## Cross-doc contradictions to watch for around chat vs. frontend
Before this pass, `documentation/frontend/overview.md`,
`documentation/architecture.md`, `documentation/api/chat-endpoint.md`, and
`documentation/reference/deployment-state.md` all asserted the frontend was a
chat UI and the sole client of `POST /api/chat`. The actual frontend calls only
the deterministic retrieval API (`/api/search`, `/api/filters`, `/api/documents`,
`/api/concepts`, `/api/keywords`) and never opens the chat SSE stream at all. If
`POST /api/chat` or the frontend's API surface changes again, re-grep for
"frontend" across the whole bundle (`grep -rln "frontend" documentation/`) — the
claim "the frontend is chat's client" tends to get restated in multiple places
and needs updating everywhere at once, not just in `frontend/overview.md`.

## Deliberately left alone
`documentation/prd.md` (a `Spec` type doc, S3/S4 describe a chat interface) was
**not** rewritten to match the built frontend, even though the frontend deviates
significantly from the PRD's chat-first requirements. Product requirements are a
product decision, not something to silently rewrite during a docs-sync pass — flag
this as Uncertain/out-of-scope rather than editing prd.md, unless a future
instruction explicitly asks for the PRD itself to be brought current.
